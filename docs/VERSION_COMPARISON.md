# birddex3 與 skw-birdex2 比較

比較日期：2026-09-20（香港時間）。

**更新判準已依使用者要求修正：判斷版本新舊時，排除 2026-09-20 當天的所有提交與本次工作區修改，只看今天之前最近一次更新。**

## 結論先講

**排除今天的批次瘦身更新後，歷史提交仍是 `skw-birdex2` 較新；即使再排除純版權更新，其最近一輪功能更新也晚於 `birddex3`。一般手機觀鳥產品的操作與容錯設計，我也較推薦它，但該設計評估與版本日期是兩件事。**

但 **`birddex3` 擁有另一組進階功能**：互動投擲、IV/CP 個體養成、對戰、地圖頁、即時鳥框、貼圖去背、QR／分享名片。`skw-birdex2` 不是它的完整替代品，不能用資料夾名稱「2／3」判斷功能包含關係。

若要求保留目前所有功能，建議：**以本次已加固的 birddex3 為整合底，逐項移植 skw-birdex2 的可靠性與手機體驗改善，不整包覆蓋。** 本次只比較及補版權，沒有合併或修改另一個 repository。

## 2. 設計與功能比較

| 面向 | skw-birdex2 | 本工作區 birddex3 | 判斷 |
|---|---|---|---|
| 普通手機操作 | `100dvh`、safe-area、ErrorBoundary，導航較簡潔 | `h-screen`、六個導航入口，尚無同等 ErrorBoundary | **2 的手機基礎較成熟** |
| 掃描流程 | 三張連拍選清晰、亮度／模糊預檢、中等信心候選確認、後續候選匹配 | 即時鳥框 + 拍照辨識 + 互動投擲，現有流程直接處理 top-1 | **2 更注重辨識失敗與不確定情況；3 更遊戲化** |
| 相機與非同步 | 開啟前停舊串流、卸載保護、AbortController、60 秒辨識逾時、busy 隱藏導航 | 上次已修即時模型釋放與推論重疊；主拍照 API 路徑尚缺同等取消／逾時保護 | **2 的生命週期處理較完整** |
| 數位縮放 | `canvas.drawImage` 依倍率中央裁切，辨識圖片跟預覽一致 | 預覽使用 CSS scale，但 `snap` 仍畫整張 video；硬體縮放另當別論 | **目前 3 有預覽與數位拍照範圍不一致風險，優先移植修正** |
| 照片／存檔 | 照片縮到 480px；quota 不足捕捉例外，降級不保存照片 | 照片與去背 dataURL 保存在 localStorage，`saveStored` 未捕捉 quota 錯誤 | **2 較耐用，但丟照片的降級不符合嚴格零資料損失** |
| XP 進度條 | 以等級起點與終點計算 | 仍用 `getLevelFromXp(xp - 1).nextXp` 推起點，等級區間內可能得到零分母 | **2 已有修正，3 應優先移植** |
| 長期參與 | 每日登入、每日任務、成就牆、熱點蓋章、夥伴鳥、音效、照片牆 | 沒有上述完整系統 | **2 更適合培養觀鳥習慣** |
| 進階養成與工具 | 無 v3 的個體 IV/CP、專用投擲／對戰／Leaflet 地圖／去背頁面功能 | 有上述功能及名片 QR、匯圖分享 | **3 的進階功能更豐富** |
| PWA 圖示 | 192/512 PNG、apple touch icon | 主要用 SVG favicon | **2 的圖示配置對手機安裝較周全** |
| 部署可重現性 | `npm install`；防增肥在獨立 `check` | `npm ci`；正式 build 自動檢查 `dist` 容量與漏入檔案 | **本工作區 3 的部署守門較嚴格** |
| 自動回歸 | 型別／lint／來源瘦身檢查 | 型別／lint／18 項 Node 測試、CI、另有選用瀏覽器 smoke | **本工作區 3 的自動化較完整** |

### 「辨識設計更好」不等於已證明準確率更高

`skw-birdex2/api/analyze.js` 有選配 `SPECIES_MODEL_2`，信心不足時可再試另一模型。但其邏輯會比較不同模型的 top score，這不是經校準的科學驗證；需實際鳥照測試集評估誤判率，不能只因有第二模型便保證更準。

### 視覺設計的判斷範圍

兩版都是深色霓虹卡牌風格。此處「2 較成熟」指根據程式檢視確認的手機尺寸、安全區、載入／失敗／候選流程與資訊負擔，**不是已做兩版實機視覺評分**。3 的六個導航與進階模式增加能力，也增加操作複雜度；兩者適合不同產品目標。

## 3. 鳥種資料：2 有後續整理，但不宜盲目覆蓋

直接按 `id` 比對兩份 `src/data/birds.json`：

- 兩邊都是 **569 種**，ID 集合相同。
- **124** 筆中文名不同。
- **45** 筆英文名不同。
- **43** 筆學名不同。
- **0** 筆 `photoUrl` 不同。

例如 `id=9/12/16/21` 在 3 仍有 `Unknown Species`／`Scientific Name` 佔位資訊，而 2 已填具體名稱；這些都是值得優先審核的候選更新。

這證明資料有後續整理，**不代表本次已獨立核實每一筆鳥名及圖片對應正確**。應核對圖片與 species ID，再以差異表移植，同步 aliases；避免舊捕捉紀錄突然被換成不相干鳥種。

## 4. 真正建置大小（同一環境 npm ci）

| 項目 | skw-birdex2 | birddex3（本次版權補齊後） |
|---|---:|---:|
| `npm run check` | 通過（型別＋防增肥） | 通過（型別＋18 項測試） |
| `npm run lint` | 通過 | 通過 |
| `npm run build` | 通過 | 通過，仍有既有大型 chunk 提示 |
| `dist` 原始檔案合計 | **1,174,470 B ≈ 1.12 MiB** | **28,484,031 B ≈ 27.16 MiB** |
| 產物數量 | 13 | 13 |
| 必要大型 WASM | 無 v3 去背 WASM | **23,914,392 B ≈ 22.81 MiB** |

2 的輸出約為 3 的 **1/24**，但不是「同功能省了 96%」：它根本沒有 v3 的 TensorFlow 即時偵測／ONNX 去背等進階功能。不能直接用總包大小評斷同功能的工程效率，也不能把改用 2 當成無功能倒退的瘦身方法。

2 的 `check-slim.cjs` 還明確把 `@tensorflow/tfjs` 列入禁止依賴；這條規則若原樣移植至 3，會與已存在的即時辨識功能衝突。

大小為未壓縮靜態檔案，不是網路實際流量、Functions bundle、Vercel 帳單或全站安裝體積。

## 5. 我建議怎樣選

### 若只要一般觀鳥者的輕量拍照收集產品

優先考慮 **skw-birdex2**：掃描容錯、手機體驗、登入任務與鳥名資料的更新比較完整，且容量小。但仍需正式金鑰、真實照片與實機驗收，不能僅憑 build 成功就宣稱全無 bug。

### 若要保留目前 v3 的全部功能（符合前一任務的零倒退限制）

繼續用 **目前已加固的 birddex3**，分批移植：

1. **P0：正確性與存檔**：數位 zoom 真正裁切；XP 進度公式；相機串流與取消／逾時；照片容量策略與 ErrorBoundary。照片不應默默丟掉，較長期可設計 IndexedDB 儲存／匯出備份，而非直接複製 2 的丟照片降級。
2. **P1：手機與資料**：`dvh`、safe-area、標準 PWA icon；核對 569 種鳥種與 aliases 的差異。
3. **P2：辨識與參與**：連拍選清晰、候選確認、任務、成就、夥伴鳥，逐項加測再接入。
4. 保留 3 的模型、個體值、投擲、對戰、地圖與去背；保留正式 build 容量門檻與現有回歸測試。

**不建議直接複製整個 `useCollection.ts`、`types.ts` 或 `ScannerScreen.tsx`。**

2 使用 `bd_collection_v2`，3 使用 `bd_collection_v3` 並做簡單 v2 遷移；兩邊又共享若干 profile/settings key。色違機率／欄位也不同：2 為 `1/64` 的收集層級機制，3 為 `1/512` 的個體 stats。若換到不同網域，localStorage 更不會自動轉移。合併前必須明確決定 schema、遊戲平衡與資料遷移規格。

上面列出的 3 的剩餘缺陷，是本輪跨版本審查的新發現／待辦；**前一輪的測試通過不等於已覆蓋這些邊界**。本次沒有擅自改變拍照、存檔或遊戲規則。
